05Template & layout tùy biến

Marketing chọn 1 template chung, rồi tùy biến khung layout cho từng slug mà không cần dev. Dev chỉ viết template một lần, mọi slug dùng lại.

Ba lớp tùy biến

1. Template (dùng chung)

Dev tạo. Là khung layout gồm các vùng có tên cố định: header, hero, main, footer. Quy định vùng nào được chứa loại block nào.

2. Theme (theo slug)

Màu, font, bo góc, kiểu nút. Mặc định lấy từ template, slug chỉ ghi phần muốn đổi. Render thành CSS variables nên không cần code thêm.

3. Layout (theo slug)

Block nào nằm ở vùng nào, thứ tự ra sao, và kiểu hiển thị của vùng: list, grid-2 hoặc carousel.

Ví dụ bộ template khởi đầu

classic

Profile trên cùng, danh sách link. Giống Linktree, hợp page ít nội dung.

heromain · carousel

video-first

Video viral to nhất ở trên, sản phẩm vuốt ngang bên dưới. Hợp page TikTok.

main · grid-2

shop-grid

Lưới sản phẩm 2 cột có thumbnail. Hợp page bán hàng nhiều sản phẩm.

Template manifest: một file, hai nơi dùng

// templates/video-first/template.json
{
  "id": "video-first",
  "name": "Video lên đầu",
  "desktop": "split",          // bố cục màn rộng ≥760px: center | split | grid
  "desktopColumns": 2,
  "regions": {
    "header": { "allow": ["profile"] },
    "hero":   { "allow": ["hero-video", "video", "release"], "max": 1, "rank": false },
    "main":   { "allow": ["card", "carousel", "link", "shop", "products", "events", "video", "banner"],
              "variants": ["carousel", "list", "grid-2"], "defaultVariant": "carousel", "rank": true },
    "footer": { "allow": ["link", "subscribe"], "rank": false }
  },
  "themeDefaults": { "bg": "#282828", "accent": "#CBD77E", "font": "Sora", "radius": 24, "button": "pill" }
}
Astro đọc manifest để render đúng vùng. Dashboard đọc cùng manifest để biết vùng nào kéo thả được block gì, có bao nhiêu chỗ, có những variant nào. Thêm template mới chỉ cần thêm 1 thư mục, không phải sửa dashboard. Bố cục desktop (desktop, desktopColumns) là thuộc tính của template, slug không tự chọn riêng. Bản mẫu chạy được: demo/templates/*/template.json.

Quyết định: có giữ chế độ "thứ tự thủ công" không?

Không giữ ở mức toàn trang

Chế độ "thủ công cả trang" tắt luôn việc tự đẩy content viral, đi ngược mục tiêu 5. Nó cũng không biết block nào thuộc vùng nào, dễ kéo card lên trên hero.

Giữ ở mức từng vùng, bằng cờ rank

  • Mặc định theo manifest: hero và footer giữ đúng thứ tự kéo thả, main tự xếp theo ghim → viral score → mới nhất.
  • Slug được ghi đè: "layout": { "main": { "rank": false } } khi muốn cố định cả vùng (vd. trang sự kiện).
  • Muốn cố định 1 card trong vùng đang tự xếp: dùng Ghim. Thứ tự kéo thả là thứ tự gốc, dùng để phân định khi score bằng nhau.

Yêu cầu riêng cho link-in-bio

Siêu nhẹ

Phần lớn người dùng mở trong in-app browser FB/TikTok. JS dưới ~50KB, ảnh WebP/AVIF, lazy load.

Mobile-first

Responsive cả desktop. Test trên webview thật: autoplay video, mở link ngoài.

Stack chốt

Astro (SSG) render HTML lúc build. JS phía trình duyệt viết bằng vanilla JS, compile bằng Google Closure Compiler. Host trên Amazon S3 + CloudFront.

Astro có còn phù hợp không? Có, và hợp hơn khi có template

Nhu cầuAstro đáp ứng thế nào
Nhiều template, chọn theo slugMỗi template là 1 layout .astro. Trang [slug].astro đọc field template rồi chọn layout tương ứng.
Build từng slug từ JSONgetStaticPaths() sinh 1 trang cho mỗi slug. Content collections đọc JSON và kiểm tra schema (zod), nên config sai bị chặn ngay lúc build thay vì ra trang lỗi.
Gần như 0 JSMặc định Astro không gửi JS xuống trình duyệt.
Theme theo slugGhi theme thành CSS variables trên :root. Template chỉ dùng biến, không hard-code màu.

Cần lưu ý: Astro mặc định build cả site mỗi lần. Với khoảng 100 slug static thì vẫn ổn, nhưng cần đo thực tế. Nếu chậm: chỉ upload lên S3 các file thực sự thay đổi, hoặc build theo danh sách slug đã đổi.

Next.js

Gửi kèm React runtime xuống client, không hợp Closure ADVANCED. Loại cho landing, nhưng dùng cho dashboard (mục 7).

11ty

Script Node tự viết

Kiểm soát tối đa nhưng phải tự làm routing, template, dev server. Không đáng.

Yêu cầu bắt buộc: chạy tốt qua Google Closure Compiler

JS phía client phải chạy đúng sau khi compile ở chế độ ADVANCED_OPTIMIZATIONS. Chế độ này đổi tên biến và thuộc tính để file nhỏ nhất, nên rất dễ làm hỏng code nếu không viết theo quy tắc.

Dữ liệu JSON: truy cập bằng chuỗi

Dùng block["thumbnail"] thay cho block.thumbnail. Nếu không, Closure đổi tên thuộc tính và đọc sai dữ liệu từ /{slug}.json.

Thư viện ngoài: khai báo externs

GA4 gtag, dataLayer và mọi API bên ngoài phải có file externs để Closure giữ nguyên tên.

Hàm gọi từ HTML: export rõ ràng

Hàm cần gọi từ bên ngoài thì gán bằng window["renderBlocks"] = renderBlocks, không để Closure đổi tên.

Tránh code "động"

Không dùng eval, không ghép tên thuộc tính lúc chạy. Hạn chế thư viện npm: phần lớn không tương thích ADVANCED mode.
Hệ quả cho stack: React/Next.js gần như không compile được ở ADVANCED mode, nên phần chạy trên trình duyệt nên là vanilla JS (có JSDoc type để Closure kiểm tra kiểu). Trong CI, chạy test headless trên bản đã compile, không chỉ trên source, vì lỗi đổi tên chỉ xuất hiện sau khi compile.

08Tracking

Biết traffic đến từ đâu và card nào hiệu quả, rồi đưa dữ liệu ngược vào thuật toán xếp hạng.

Nguồn traffic

  • Mỗi page nguồn = 1 slug riêng (/fanpage-abc), nên không phụ thuộc referrer (in-app browser hay làm mất referrer)
  • Gắn UTM vào banner Linktree

Click event

  • GA4 + navigator.sendBeacon: gửi slug, blockId, vị trí card
  • Không đi qua trang redirect /go/... để tránh thêm độ trễ
Vòng phản hồi: click → viral score → card được bấm nhiều tự lên trên.

Nhiều người cùng quản lý nhiều page, nên cần phân quyền ngay từ bản đầu có backend. Giữ đơn giản: 3 vai trò, giao quyền theo từng slug.

Chỉ Admin được đổi tên slug

Slug chính là URL mà banner Linktree đang trỏ tới. Đổi slug mà quên sửa Linktree thì toàn bộ traffic của page đó vào trang lỗi. Khi đổi, tự tạo redirect từ slug cũ.

Lịch sử phiên bản + rollback

Mỗi lần Publish lưu 1 bản JSON. Ai sửa sai thì quay lại bản trước trong 1 bấm, và có log ai sửa gì, lúc nào.

Draft → Publish

Sửa ở bản nháp, xem preview, rồi mới Publish để trigger rebuild. Chưa cần bước duyệt; thêm sau nếu team lớn.

Lộ trình

Mock UI: chưa cần đăng nhập. Bản có backend: thêm 3 vai trò trên. Sau đó mới tính nhóm slug theo brand/team nếu số page tăng mạnh.
Đã có trong demo (demo/editor.html): trạng thái bản nháp / đang chạy, nút Publish kèm tóm tắt thay đổi và ghi chú, Lịch sử phiên bản (ai publish, lúc nào, thay đổi gì), Khôi phục = publish lại nội dung bản cũ thành phiên bản mới, lịch sử không bị xóa. Demo lưu ở localStorage và chỉ giả lập webhook build; bản thật cần bảng versions trong DB và gọi webhook build lại slug.

10Rủi ro & câu hỏi

Những điều cần theo dõi và cần team làm rõ.

Domain chưa được tin cậy

Link trỏ thẳng về domain mới dễ bị FB/TikTok đánh dấu. Vì vậy vẫn cần Linktree làm bước trung gian. Nên dùng domain cũ, có HTTPS, có nội dung thật.

Thêm 1 bước bấm

Dữ liệu

  • Bảng products (url gốc, affiliateUrl, mạng, tên, ảnh, giá, tiền tệ, ẩn/hiện) và collections (danh sách id có thứ tự), dùng chung cho mọi slug.

Lấy metadata

  • Không lấy được (sàn chặn bot, trang render bằng JS) thì hiện form điền tay; affiliate link vẫn tự tạo.
  • Shopee/Lazada nên dùng API của sàn hoặc headless browser. Bản mẫu: demo/tools/meta-server.js.

Affiliate link

  • Bản thật gọi API tạo link của từng mạng (Shopee, Lazada có API cho publisher). Demo chỉ gắn tham số giả + UTM.
  • Bấm sản phẩm đi thẳng tới affiliate link, không qua /go/ (giữ nguyên quyết định ở mục 8); tracking qua GA4 + sendBeacon với blockId = id sản phẩm.

Cần xác nhận

  • Tài khoản affiliate của từng sàn, ai giữ ID.
  • Hoa hồng thật lấy từ báo cáo của sàn; số trên dashboard demo chỉ là ước tính.
  • Giới hạn 20 sản phẩm / bộ sưu tập (theo cách Linktree làm) có phù hợp không.
